## 复现

建立 edition 2024 的临时 Cargo 二进制项目，将依赖分别命名为 `old` 和
`new`，均设置 `package = "qubit-batch"`，路径指向基线和候选 checkout。
将两者放在同一个 rs-progress checkout 旁，使相对路径依赖解析为同一包。
执行 `cargo run --release`。完整探针源码见[英文版的复现章节](performance.md#reproduction)，
两种语言共用该源码。探针不创建工作线程，避免其它分配与计数重置竞争。

## 调度工作负载

`cargo bench --bench scheduling_matrix_bench` 比较顺序执行器和 scoped
执行器。普通组测量单次调用；`end-to-end-concurrent-*` 包含调用线程的
创建和 join；`steady-callers-*` 在计时前创建并复用调用线程，但计入请求与
结果通道的交接开销。两者均在计时前验证正确性。标准执行器自身的工作线程
创建仍计入所有组的每次批次调用。使用 `cargo bench --bench
scheduling_matrix_bench -- --test` 运行正确性冒烟检查。这些工作负载不测量
Rayon；其基准位于 rs-rayon-batch。

## 不透明逐步屏障 CPU 负载（2026-10-28）

CPU 基准组的新名称为 `batch_executor_cpu_opaque_steps`。256 次 wrapping
乘加中的每一步都将中间值传入 `black_box`，阻止编译器合并相邻步骤。使用
Rust 1.94.0 release 编译的小型探针确认：旧循环每次循环迭代执行 8 次递推，
新负载则每次迭代保留一次递推。种子为 1 时的终值为
`4899730818626408193`。屏障本身也有成本，因此这些数值只描述该受控负载，
不代表一般应用的 CPU 吞吐量。注册计时项之前，基准代码本身还会检查
`CpuTask { seed: 1 }` 的结果是否等于这个固定值。

测量日期为 2026-10-28，工具链为 `rustc 1.94.0 (4a4ef493e 2026-03-02)`、
LLVM 21.1.8，release 构建；环境为 Linux x86_64 7.0.0-38-generic 和六核
Intel Core i5-9600K。基准源码基于 HEAD
`bc25180e5c845bfaef30c5964838a0982a442b6f`，并包含
`benches/batch_executor_bench.rs` 中本轮负载、组名及计时外验证的未提交改动
（SHA-256 `1c3cf5ce1c7b7aa6b78c26c688a81a8f54425880cad04691cc4fe8fdd18a6b04`）。
`Cargo.lock` 的 SHA-256 为
`e63e6e0b44496482d2460b26f8a7c2bd2564bef938770437cd0b32993e517121`。

命令：`cargo bench --locked --bench batch_executor_bench -- batch_executor_cpu_opaque_steps`。
Criterion 0.8.2 使用默认设置：每点 100 个样本、预热 3 秒、请求测量 5 秒、
置信区间为 95%。表格列出每批耗时的估计值及 95% 置信区间，单位为毫秒。
部分 workload 无法在请求时长内完成 100 个样本；Criterion 报告了较宽的区间和
离群值，强制并行路径尤其明显。应将数据视为本机噪声较大的快照，不能据此可靠排序。
