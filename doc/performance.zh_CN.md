# 性能测量

[English](performance.md) · [设计说明](design.zh_CN.md)

## 失败索引校验

测量日期为 2026-09-07，使用 Rust 1.94.0、release profile、Linux x86_64
和六核 Intel Core i5-9600K。基线为提交 `2067172`（qubit-batch 0.10.0），
候选版本为 0.11.0 的原地排序实现。输入包含 F 个失败任务，索引唯一且逆序。
输入向量的构造和销毁不计入 build 测量区间。单线程进程包装系统分配器，
统计分配和重新分配请求，在调用 `build()` 前立即重置计数。

每个规模重复三次，结果完全一致：

| F | 基线分配次数 | 基线请求字节数 | 候选分配次数 | 候选请求字节数 |
|---:|---:|---:|---:|---:|
| 1,000 | 1 | 18,448 | 0 | 0 |
| 10,000 | 1 | 147,472 | 0 | 0 |
| 100,000 | 1 | 1,179,664 | 0 | 0 |

这些数值表示校验过程中的额外分配请求，不是结果总内存或进程驻留内存。
结果仍持有 O(F) 的失败向量。可重复的分配减少是移除辅助 HashSet 的依据。
错误优先级变化见[迁移说明](design.zh_CN.md)。

Criterion 耗时没有得到确定结论：100,000 条失败记录的基线点估计为
2.0654 ms，候选两次为 0.3395 ms 和 3.63 ms。未受控环境不能证明可重复的
加速，因此不能据此选择并行阈值或宣称吞吐量提升。

## 复现

建立 edition 2024 的临时 Cargo 二进制项目，将依赖分别命名为 `old` 和
`new`，均设置 `package = "qubit-batch"`，路径指向基线和候选 checkout。
将两者放在同一个 rs-progress checkout 旁，使相对路径依赖解析为同一包。
执行 `cargo run --release`。完整探针源码见[英文版的复现章节](performance.md#reproduction)，
两种语言共用该源码。探针不创建工作线程，避免其它分配与计数重置竞争。

## 调度工作负载

`cargo bench --bench scheduling_matrix_bench` 比较顺序执行器和 scoped
执行器。普通组测量单次调用；`end-to-end-concurrent-*` 包含调用线程的
创建和 join；`steady-callers-*` 在计时前创建并复用调用线程，但计入请求与
结果通道的交接开销。两者均在计时前验证正确性。标准执行器自身的工作线程
创建仍计入所有组的每次批次调用。使用 `cargo bench --bench
scheduling_matrix_bench -- --test` 运行正确性冒烟检查。这些工作负载不测量
Rayon；其基准位于 rs-rayon-batch。

## Callable 回退测量（2026-09-09）

环境为 Intel Core i5-9600K（6核）、Linux x86_64 7.0.0-30-generic、Rust 1.94.0 /
LLVM 21.1.8、release 构建和 NoopReporter。基线是 qubit-batch `62e2a3d` 与
qubit-rayon-batch `99ce8c5`，覆盖相同的新 benchmark 源文件；两组都使用本地
qubit-progress 0.8.3。改进版本加入直接顺序 callable 收集及缓冲区复用，生产 Rayon
共享队列保持原样。

运行 `cargo bench --locked --bench call_fallback_bench` 可覆盖 0/1/32/100/101/1024 项、
标量和 String 返回值，以及双 worker（阈值100/0）和单 worker（阈值0）配置。执行器在
计时外创建，标准并行路径每次调用创建 scoped worker 的成本仍包含在内。每点20个样本、
预热200毫秒、请求测量500毫秒；计时前校验成功数和输出数，计时包含结果析构。

部分结果如下，单位为微秒，方括号内为均值的95%置信区间：

| 配置 / 项数 | 基线均值 [95% CI] | 改进均值 [95% CI] |
| --- | ---: | ---: |
| default / 32 | 4.013 [3.971, 4.062] | 2.520 [2.507, 2.533] |
| default / 100 | 11.293 [11.199, 11.401] | 7.052 [7.008, 7.095] |
| one-worker / 1024 | 108.982 [107.303, 111.160] | 62.852 [62.440, 63.312] |
| parallel / 1024 | 2086.781 [2045.877, 2141.154] | 2073.002 [2055.272, 2093.523] |

这些数据来自本机串行测量，不构成通用加速承诺。线程创建与系统调度会明显影响强制并行的
极小批次，不应据此修改默认阈值100。Criterion 原始估计与样本保存在 `target/criterion`；
复测基线时应使用相同 benchmark 源码和依赖检出版本。

## 分块缓冲区的分配请求

单线程全局分配器探针仅统计 `process_with_count` 期间的分配/重分配请求；delegate 消费 u64，
使用 NoopReporter。输入 range 和 processor 的构造不在统计区间内。三次结果完全相同。
这些是整个调用的分配请求，不是驻留内存，也不是只统计 Vec 的扩容次数。

| 项数 | 块大小 | 旧请求数 | 旧请求字节数 | 新请求数 | 新请求字节数 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1024 | 1 | 1031 | 33220 | 8 | 484 |
| 1024 | 16 | 197 | 14716 | 8 | 604 |
| 1024 | 256 | 29 | 14716 | 8 | 2524 |
| 1024 | 4096 | 8 | 8668 | 8 | 8668 |
| 65536 | 1 | 65543 | 2097604 | 8 | 484 |
| 65536 | 16 | 12293 | 917884 | 8 | 604 |
| 65536 | 256 | 1793 | 1038844 | 8 | 2524 |
| 65536 | 4096 | 173 | 1015804 | 8 | 33244 |

`cargo bench --locked --bench chunk_buffer_bench` 用相同规模测量耗时，每点20个样本、
预热200毫秒、请求测量500毫秒。复用容量消除了每块重新增长缓冲区的请求，但进度初始化
仍有分配。复现实验可使用[英文版所附完整探针](performance.md#chunk-buffer-allocation-requests)，
在独立 Cargo binary 中依赖待测检出版本并运行 `cargo run --release`；探针进程内不得并行
运行其他产生分配的线程。
